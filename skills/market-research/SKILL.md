# 教育科技市场调研规范（Discovery 阶段）

本 SKILL 覆盖工作流第 2 步「教育科技市场竞品调研 → 产出调研报告 → 划定核心能力模块」，由 Value Architect 在 Mode 2 下显式 Read 并执行。

核心目的不是穷举市场，而是 **辅助 PM 做价值判断**：既看清竞品的核心能力与痛点（自下而上），也看清市场容量、趋势与分群（自上而下），最终汇聚为一张"核心能力模块图"，决定我方是否要做、做什么、为谁做。

---

## §0 调研模式（先选范围）

| 模式 | 产物 | 何时用 |
|---|---|---|
| **Mode A · 竞品对标** | 竞品速览表 + 1–2 家深度对标（§1–§3） | 已有明确竞品 URL，聚焦"别人怎么做" |
| **Mode B · 市场全景** | 市场容量 TAM/SAM/SOM + 趋势 + 用户分群（§2X） | 需要判断"市场有多大、往哪走、给谁做" |
| **核心能力模块划定** | 能力模块图（§2Y） | 上述任一/全部完成后**必做**，作为 Value Architect 的核心 handoff |

> **默认建议 A + B 都做**，再用 §2Y 汇聚。若 PM 时间紧或只要其一，按 PM 指定执行，但 §2Y 核心能力模块划定**不可跳过**——它是给 Value Architect Gate 2 的关键输入。

| 输入项 | 说明 | 是否必须 |
|---|---|---|
| Project Name | PM 拟做的项目名（kebab-case，如 `ielts-b2b`） + 一句话项目描述 | ✅ |

| 地域偏好 | 国内 / 海外 / 全部 | ⭕ 默认全部 |

## §2 三步调研流程（强制执行顺序）

### Step 1：读取 PM 提供的竞品 URL

本仓库当前 **不依赖 web search 自动发现竞品**。Step 1 的工作是：

1. 接收 PM 提供的 ≥3 个竞品 URL
2. 对每个 URL：
   - 若 `web/fetch` 可用 → 抓取页面正文，提取产品定位、能力、用户、痛点信号
   - 若 `web/fetch` 不可用 → 要求 PM 粘贴该竞品的关键介绍文字（官网首页、产品页 hero / feature 段落）
3. 整理为待入表的候选竞品清单（名称 + URL + 一句话识别理由）

禁止：在 PM 未提供 URL 时凭记忆或臆测列竞品；如 PM 提供数量不足，向 PM 追问补足，不自行编造。

### Step 2：竞品速览（每竞品一行，核心能力与解决的痛点两列并列）

对 Step 1 候选清单中每个竞品产出一行速览，落盘到 `Project/{project}/Research/competitor-shortlist.md`：

```markdown
# Competitor Shortlist — {project}

> Created: {YYYY-MM-DD-HHmm}
> Project: {project}
> Strategy: {pillar}
> Discovery Keywords: {keywords used in Step 1}

| # | 竞品名称 | 产品速览 | 核心能力 | 解决的痛点 | 优势定位 | 不足之处 | 整体评价 | URL |
|---|---|---|---|---|---|---|---|---|
| 1 | Competitor A | [≤30 字定位] | 1) ... 2) ... 3) ... | 1) ... 2) ... | 1) ... 2) ... | 1) ... 2) ... | [适合借鉴 / 不适合] | https://... |
| 2 | Competitor B | ... | ... | ... | ... | ... | ... | ... |
| 3 | ... | ... | ... | ... | ... | ... | ... | ... |
```

**字段强制要求：**

| 字段 | 内容标准 |
|---|---|
| **产品速览** | 一句话定位（≤30 字，包含目标用户 + 核心价值主张） |
| **核心能力** | 3–5 项核心能力（动词短语，如"AI 口语自动评分" / "考前批量发码" / "数据看板回看"） |
| **解决的痛点** | 该竞品针对的用户具体痛点（≤3 条，必须可感知，如 "自学者缺少即时反馈" / "练完不知道自己处于什么水平" / "找老师批改成本高"），与"核心能力"对应列写，避免空话 |
| **优势定位** | 与同类相比的差异化点（≤3 条，强调差异化非通用能力） |
| **不足之处** | 已知短板 / 缺失能力 / 不适合我方借鉴的风险点（≤3 条；信息不足时标 `[待确认]`） |
| **整体评价** | 适合借鉴 / 部分借鉴 / 不适合（含一句话理由） |
| **URL** | 官网或主要产品页（可访问的最相关 URL） |

### Step 3：PM 选定 1-2 家深度对标

呈现 Step 2 表格给 PM，由 PM 选定 1–2 家进入深度对标。对每家选定竞品产出独立的 6 段式 Summary，落盘到 `Project/{project}/Research/competitor-{name}.md`：

#### Section 1：产品速览
- 产品名称 / 公司 / 一句话定位
- 核心用户群（具体到行业 / 职能 / 体量）
- 主要使用场景（≥3 个典型场景）
- 商业模式（订阅 / 流量 / 一次性付费 / 免费 等）

#### Section 2：核心能力
- 列出 5–10 个核心能力（按重要性排序）
- 每个能力配 1 句描述（避免空泛 - 必须可观察可验证）

格式：
```
1. 能力名称 — [一句具体描述，含触发条件 / 输入 / 输出]
2. ...
```

#### Section 3：解决的痛点
- 列出该竞品聚焦的 3–5 个用户痛点
- 每条痛点必须包含：① 是谁的痛点（具体用户角色 / 场景）；② 痛点的具体表现；③ 该竞品用哪个核心能力解决（与 Section 2 对应）
- 来源标注：用户评论 / 官网营销文案 / 自身测试 / 行业分析

#### Section 4：优势定位
- 与同类产品差异化点（3–5 条）
- 每条注明：① 优势性质（技术 / 数据 / 生态 / 价格 / 体验）；② 难复制度（高 / 中 / 低）

#### Section 5：不足之处
- 已知痛点 / 用户反馈差评 / 缺失能力（3–5 条）
- 每条注明来源（用户评论 / 自身测试 / 行业分析）

#### Section 6：整体评价（最重要）
- **适合借鉴**：针对我方场景的具体设计 / 流程 / 字段（条目化）
- **不适合借鉴**：哪些做法在我方场景会失败（条目化 + 原因）
- **推荐截取的核心能力清单**：从 Section 2 中筛选出我方可复用的能力（≤5 项），为 Value Architect Gate 2 提供输入
- **推荐承接的痛点清单**：从 Section 3 中筛选出我方可解决的核心痛点（≤5 项），为 Value Architect Gate 2 "PM 必答四问" 提供输入

## §2X 市场全景调研（Mode B）

目的：给 PM 一张"市场有多大、往哪走、给谁做"的全景，避免只看竞品而误判市场盘子与方向。产出落盘到 `Project/{project}/Research/market-landscape.md`。

> **数据纪律（强制）**：市场容量与趋势必须**有据可查**。优先级：① PM 提供的行业报告 / 内部数据 ② `web/fetch` / web search 可用时检索权威来源（行业报告、统计局、上市公司财报、Statista/艾瑞/弗若斯特沙利文等），每个数字标注**口径 + 年份 + 来源 + 币种**。无可靠来源时显式标 `[待确认 · 需补来源]`，**禁止编造数字**。

### §2X.1 市场容量 TAM / SAM / SOM

| 层级 | 定义 | 本项目口径 |
|---|---|---|
| **TAM** 总体市场 | 该品类全部潜在需求规模 | 如"中国雅思/英语测评备考全市场年规模" |
| **SAM** 可服务市场 | 受我方产品形态 / 地域 / 语言 / 渠道约束后可触达的部分 | 如"我方小程序+B端可服务的细分" |
| **SOM** 可获得市场 | 1–3 年内现实可拿下的份额 | 如"首年可获取的考生数 × ARPU" |

**估算方法（至少给一种，推荐两种交叉验证）：**

```
Top-down：行业报告总量 × 适用比例（地域/人群/产品形态层层收窄）
Bottom-up：目标用户数 × 渗透率 × ARPU（客单价 × 频次）
```

落盘模板：

```markdown
## 市场容量
| 层级 | 规模 | 估算法 | 关键假设 | 来源（口径/年份/币种） |
|---|---|---|---|---|
| TAM | ¥X 亿 | Top-down | ... | 艾瑞 2025 在线教育报告 |
| SAM | ¥Y 亿 | Bottom-up | 渗透率 z% | ... |
| SOM | ¥Z 万 | Bottom-up | 首年获客 n 人 × ARPU | 内部测算 [待确认] |
```

### §2X.2 市场趋势（PESTEL-lite）

至少覆盖 4 个维度，每条注明**信号来源** + **对我方的 implication**：

| 维度 | 关注点（示例） |
|---|---|
| **技术** | LLM / AI 自动评分成熟度、语音识别、Agent 化学习 |
| **政策** | 教育监管、留学/雅思考试政策、数据合规（个保法） |
| **用户行为** | 自学化、移动化、短时高频、社区化备考 |
| **商业模式** | 订阅制、B2B2C、机构合作分成、内容付费 |

```markdown
## 市场趋势
| 维度 | 趋势 | 信号来源 | 对我方 implication（机会/威胁） |
|---|---|---|---|
| 技术 | AI 口语评分进入可商用精度 | 竞品 X 已上线 / 论文 | 机会：可作为差异化核心能力 |
```

### §2X.3 用户分群（Segmentation）

按用户类型切分，标注规模、需求差异、付费意愿，并圈定**我方目标段**（须与战略归属一致）：

```markdown
## 用户分群
| 细分 | 典型用户 | 规模/占比 | 核心需求 | 痛点 | 付费意愿 | 我方目标段 |
|---|---|---|---|---|---|---|
| TOC-自学备考 | 在校生/职场考生 | ... | 即时反馈、低成本 | 缺反馈、不知水平 | 中 | ✅ 主目标 |
| TOC-高分冲刺 | 目标 7+ | ... | 精准批改 | 找老师贵 | 高 | ✅ |
| TOB-机构 | 培训机构 | ... | 批量管理、提分数据 | 师资成本高 | 高 | ✅ 第二曲线 |
| TOB-院校 | 高校/国际部 | ... | 测评标准化 | ... | 中 | ⭕ 观察 |
```

## §2Y 核心能力模块划定（必做 · 核心 Handoff）

把 §3 竞品核心能力（自下而上）与 §2X 市场需求/分群痛点（自上而下）**汇聚成能力模块**，落盘到 `Project/{project}/Research/capability-modules.md`。这是工作流第 2 步「划定核心能力模块」的直接产物，也是 Value Architect 划 Roadmap / Epic 的输入。

```markdown
# Core Capability Modules — {project}

> Created: {YYYY-MM-DD-HHmm} · Strategy: {pillar}

| 模块 | 覆盖痛点（来自 §2X.3 / §3） | 竞品覆盖情况 | 我方差异化机会 | 战略归属 | 优先级 |
|---|---|---|---|---|---|
| M1 AI 口语自动评分 | 自学者缺即时反馈 | A 有 / B 弱 / C 无 | 中文母语者口音优化 | ai_assessment | **P0** |
| M2 备考路径规划 | 不知自己水平/下一步 | 多数仅题库 | 与评分联动个性化 | ai_assessment | P1 |
| M3 机构管理后台 | 机构批量管理成本高 | A 有 B 端 | 与考试交付打通 | ai_assessment(TOB) | P1 |
| M4 ... | ... | ... | ... | ops_excellence | P2 |
```

**字段强制要求：**

| 字段 | 标准 |
|---|---|
| 模块 | 能力簇而非单点功能（动词+对象，可独立产生用户价值） |
| 覆盖痛点 | 必须可回溯到 §2X.3 分群痛点或 §3 竞品 Section 3 痛点 |
| 竞品覆盖情况 | 标明"谁有/谁弱/谁无"，体现空白与红海 |
| 我方差异化机会 | 一句话说清为什么我方能做得不一样/更好 |
| 战略归属 | ops_excellence / test_delivery / ai_assessment（对齐公司三大方向） |
| 优先级 | P0（核心差异化必做）/ P1（重要）/ P2（观察），并给一句理由 |

**DoD（落盘前自检 · 阻塞）：**

- [ ] 每个模块的"覆盖痛点"都能回溯到 §2X.3 或 §3 的具体痛点条目，无悬空模块
- [ ] 至少 1 个 P0 模块，且其"我方差异化机会"非通用能力（不能是"也有题库"这类红海描述）
- [ ] 每个模块标了战略归属，且与本项目 §1 战略归属自洽
- [ ] 模块数 3–7 个（过多说明未聚焦，过少说明覆盖不足）

## §4 数据来源与可验证性

调研内容必须满足：

- **可追溯**：每个 Section 的关键论断附引用源（URL / 报告名 / 测试日期）
- **可观察**：能力描述基于公开可验证的产品功能，禁止凭空推断
- **避免广告语**：不使用厂商营销话术，需要转译为客观描述
- **不确定标注**：信息不足时显式标 `[待确认]`，不强行编造

## §5 Gate 与 Handoff

### Gate（PM 确认）
- **Mode A Step 2 浅扫产出后**：PM 选 1–2 家深度对标 → 进入 Step 3
- **Mode B §2X 市场全景产出后**：PM 确认市场容量口径与目标分群 → 进入 §2Y
- **§2Y 核心能力模块图产出后**：PM 确认模块清单与优先级是否符合战略 → 进入 Value Architect Gate 2

### Handoff 到 Value Architect
**`capability-modules.md` 的核心能力模块图**是给 Value Architect 的首要 handoff：PM 在 Gate 2 据此决定哪些模块进入"我方核心能力"、如何映射到 Roadmap / Epic。`market-landscape.md` 的 TAM/SAM/SOM 与分群为 Value Frame 的"业务价值 / 目标用户 / 为什么现在做"提供事实支撑。

## §7 强制规则

必须：
- Mode A：Step 1 → Step 2 → Step 3 顺序执行，禁止跳过；Step 1 必须基于 PM 提供的 URL（或 PM 粘贴的关键文字）
- Mode A：Step 2 速览字段全部填写，"核心能力"与"解决的痛点"两列并列；Step 3 六段式全部产出
- Mode B：市场容量每个数字标注口径 + 年份 + 来源 + 币种；趋势至少 4 维度且每条带 implication；分群圈定我方目标段
- **§2Y 核心能力模块图必做**（即使只做了 A 或只做了 B），且通过其 DoD 自检
- 关键论断/数字必须附引用源；信息不足显式标 `[待确认]`

禁止：
- 在 PM 未提供 URL 或介绍文字时凭空编造竞品
- **编造市场容量数字或趋势**（无来源时标 `[待确认 · 需补来源]`，不强行给数）
- 把"核心能力"和"解决的痛点"合并为同一列或一句话写
- 用厂商营销话术替代客观描述
- 跳过 PM 选定环节，agent 自行决定深度对标对象或目标分群
- 跳过 §2Y 核心能力模块划定直接 handoff 给 Value Architect
- 不落盘只在对话中输出
